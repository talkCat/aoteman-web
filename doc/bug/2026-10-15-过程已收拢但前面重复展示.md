# 最终已收拢为「过程 · N 步」折叠块，但前面又重复展示了多个过程块

- 日期：2026-10-15 记录；2026-10-18 完成根因分析、设计并修复
- 状态：已修复（前端展示层）
- 归属仓库：`aoteman-web`（纯前端展示层改动）

---

## 一、现象（用户报告）

一轮长任务的最终形态已经是**一个可折叠的** `过程 · 20 步（含 10 次工具）` 块，展开后覆盖整轮的思考与工具调用；但同一轮里、在前面的位置又**并列铺开**了 6~7 个无计数的裸 `过程` 块（含叙述、追问问卷、工具、执行结果报告等），观感上像是「重复展示」。中间块还穿插在正文/问卷之间，打断阅读，且**无计数块与有计数块渲染形态不一致**。

## 二、取证（Chrome DevTools MCP）

### 2.1 短会话（单段叙述）

会话 `1792302720508-vqpybk8f3`（帮我做一份去成都旅游的ppt）：

- SSE 重放仅 1 条 `agent.narration`（seq=7，id `evt_24e5caac5f254d0c97f91fced53396ee`），随后 1 次 `ask_followup_questions` 工具调用，`AGENT_END`。
- DOM（`[data-turn-id="1"]`）实测：
  - 1 个裸 `过程` 块（内容即该 narration）；
  - 1 个折叠块 `过程 · 1 步（含 1 次工具）`。

### 2.2 复现长会话（多段叙述）

新会话 `1792305011028-9xuwlicsp`（东京/大阪/京都旅游季节对比），SSE 事件序列（seq）：

| seq | type | 说明 |
| --- | --- | --- |
| 5 | agent.tool_use | web_fetch |
| 10 | agent.tool_use | web_fetch |
| **17** | **agent.narration** | 「让我搜索这三个城市的最佳旅游季节和气候信息。」 id `evt_e8b9f5fd33a74f499661dee4acdf231d` |
| 18 | agent.tool_use | web_search |
| 23 | agent.tool_use | web_search |
| 31 | agent.message | 最终 Markdown 对比表 |

DOM（`[data-turn-id="1"]`）节点顺序实测：

1. 裸 `过程` 块（= seq17 的 narration）
2. 折叠块 `过程 · 4 步（含 4 次工具）`（= 4 次 tool_use）

**关键结论一：不存在同一段文本被渲染两遍。**

后端 `ConversationEventMapper` 有两条独立来源：

- `thinking` ← `ThinkingBlockDeltaEvent`（推理增量）；
- `narration` ← 「工具调用前的可见文本」，由 `flushNarration()` 落盘（复用流式气泡的 event id，并清空可见文本缓冲，二者文本不同）。

前端 `useSSEStream` 对 `agent.narration` 按 `id` 去重（`markSeen`），并在 `agent.message` 到达时跳过同名 id，也不会重复。

**关键结论二：真正的问题是「聚合与排序」，不是「重复渲染」。**

`ProcessTimeline` 把**每一段** `narration` 渲染成一个**独立、恒定可见的裸 `过程` 块**，并把这些裸块**统一提到折叠块之前**；只有 thinking+tool 进折叠块。于是：

- 一轮里 N 段叙述 → N 个裸 `过程` 块 + 1 个折叠块（长任务里模型每次工具调用前都可能输出一段可见文本，故 N 可达 6~7）；
- 裸块被提升到折叠块之前，**丢失了真实 seq 交错顺序**（上表 seq17 的叙述实际发生在 seq5/10 之后，DOM 里却排在最前）；
- 裸块无计数、折叠块有计数 → 用户观感为「两种过程块重复」。

## 三、根因（定位到代码）

`src/app/page.tsx` 的 `ProcessTimeline`（修复前 145–236 行）：

- `narrations` 单独 `map` 成裸块（恒定可见）；
- `mechanics = steps.filter(s => s.kind !== 'narration' && s.kind !== 'answer')` 进折叠块，标题 `过程 · {mechanics.length} 步（含 M 次工具）` **只统计 thinking+tool**；
- 两类块形态/口径不一致。

该形态源自早期设计 `doc/design/chat-interaction-refinement.md` §11.2-P0「叙述不应被折叠」，实现时被落地为「叙述永远裸露在最上面」，从而在长任务里退化为「多个过程块」。

## 四、影响范围

- 仅前端展示层（`aoteman-web`），**不改** `useSSEStream.ts`、`types/agent.ts`、BFF 接口与后端（设计红线）。
- 触发条件：单轮内 ≥2 次工具调用，且模型在工具调用前输出可见文本（长任务 / ReAct 多步）。

## 五、方案（已采纳）

把一轮内的「叙述 + 思考 + 工具」收敛为**同一条时间线（单一折叠块）**：

1. `ProcessTimeline` 只保留**一个**折叠容器 `过程 · N 步（含 M 次工具）`，其中 N = 叙述 + 思考 + 工具 总步数，M = 工具次数（口径比原来更准确）。
2. 容器内所有行**按真实 seq 交错**渲染，行样式保留类型区分：叙述 `MessageSquareText`＋「过程」、思考 `Sparkles`＋「思考」、工具 `ToolStep`。
3. 轮次**进行中自动展开**（`isActive`），**结束后自动收起**；用户手动开合后不再被自动覆盖（沿用 `manualOverride`）。
4. 「你的选择」（追问作答）仍在同一 `ProcessTimeline` 内，调整到时间线**之后**渲染（符合「问题 → 回答」的真实顺序）。

## 六、副作用 / 取舍

- 副作用：轮次结束后默认收起，叙述不再「常驻」；换来的是块数从 N+1 降为 1、计数口径统一含叙述、顺序还原真实 seq。
- 关于 §11.2-P0 的取舍：叙述被收进折叠块，**但轮次进行中默认展开**，叙述在「可纠偏窗口」内仍实时可见、可中断；结束后收起，用户可一键展开回看全过程。且上一轮修复「工具起始帧展示真实工具名」已保证运行中有可见进度，不会「全程沉默」。
- 替代 A（更保守）：叙述仍留在折叠块之外，但把一轮内多段叙述**合并为 1 个块**（而非每段一个）；块数 N+1 → 2。缺点：仍存在两种块形态。
- 替代 B（P0 原建议）：叙述留在折叠块外保持可见，仅当轮次含叙述时**不自动收起**。缺点：长轮次默认常展开、篇幅长。
- 若后续产品更强调「叙述常驻可见」，主方案只需一行改动即可切换为替代 B。
