1. 管理员选中「政策专家」后提问，`POST /api/sessions/{sessionId}/events` 返回 **503**，对话中断，页面同时出现渲染报错。

### 编译失败

- 当前 `src/app/admin/knowledge/[kbId]/page.tsx` 第 72 行为 `import { cn } from '@/lib/utils';`。
- 全仓库已无 `admin-preview` / `knowledge-demo` / `user-experts` 引用（`Select-String` 无命中），对应文件已删除，页面已接 `@/lib/knowledge-api`。
- 说明报错来自 Turbopack 的陈旧模块图：页面在旧版本编译产物里仍持有已删除模块的 import。

## 根因

### 503（前端缺陷，主因）

追问问卷卡片在 `agent.tool_use` 到达时就立即绑定该 `tool_use_id` 并渲染，但**没有在该工具调用转为 `error` 时失效**：

- `useEffect` 里 `if (followupQuestionnaire) return;` 让后续有效的新工具调用（`call_2a789e…`）无法替换旧问卷。
- 旧问卷的 `toolCallId` 一直指向已被服务端判定失败的 `call_88afdf…`。
- 用户点击提交，携带陈旧 `tool_use_id` 调 `resumeWithToolResult`，框架校验「收到的 id ≠ 当前挂起的 id」直接抛 `IllegalStateException` → 503。

即：**服务端只挂起一次工具调用（第二次），前端却把答案发给了第一次（已失败）的调用**。

### 编译失败（构建缓存）

删除静态 demo 数据后页面已改造完成，源码无残留引用；报错来自 dev server 进程内旧的模块图/缓存，与当前源码不一致。

## 修复方案

### 前端（`src/app/page.tsx`）

1. 问卷「仍然有效」的判定改为：其 `toolCallId` 必须仍对应一条 `status === 'pending'` 的 `ask_followup_questions` 工具；否则立即清空问卷，并允许下一个挂起调用生成新问卷。
2. 提交前二次校验：若问卷绑定的工具已不是 `pending`，不发送请求，改为提示并刷新问卷（防御服务端已失败/已替换的情况）。
3. 重置会话时清空 `handledFollowupIdsRef`，避免跨会话累积。
4. 允许「更新的同类型工具调用」取代尚未提交的旧问卷（按 `toolCallId` 与时间顺序判定）。

不改服务端接口契约：服务端对不匹配的 `tool_use_id` 报错是正确行为（避免把答案写进错误的调用）。

### 编译失败

重启 dev server 清空 Turbopack 内存模块图与 `.next` 缓存；不重新引入已删除的 demo 文件。

## 影响范围

- 仅前端 `src/app/page.tsx`（追问问卷状态机）与本地 dev 缓存。
- 不涉及服务端、数据库、接口契约。

## 验证方式

1. `npx tsc --noEmit`、`npx eslint src`、独立 `distDir` 的 `next build` 全部通过。
2. 重启 dev server 后访问 `/admin/knowledge/{kbId}` 返回 200，无 `Module not found`。
3. 页面实测：管理员登录 → 新建会话 → 选择「政策专家」→ 提问「女性职工在职场有哪些权益？」→ `POST /events` 返回 200，回答正常渲染并带知识库引用。
4. 追问场景回归：构造一次失败后又重试的 `ask_followup_questions`（5 选项 → 4 选项），确认只出现一张可提交问卷，提交后不再出现 503。

## 追加排查（2026-11-05 23:30）：专家问答 503 的第二个根因

### 现象与隔离实验

修复前端问卷状态机后，重启 dev server，用干净浏览器/干净 cookie 复测：

| 实验 | 结果 |
| --- | --- |
| 管理员提问，**不选专家** | `POST /events` **200** |
| 管理员提问，选「政策专家」 | `POST /events` **503** |
| 选不存在的专家 `exp_does_not_exist_123` | 仍然 **503**（说明请求根本没走到控制面 resolver；若走到应是 403） |

时间上 0.4s 内返回，不是超时。

### 证据

1. 数据面「不选专家」的轮次完全正常；只有 `expertIds` 非空时失败，失败点在专家解析阶段
   （`ConversationTurnService#planExpertTurn` → `ExpertTurnPlanner` → `HttpExpertControlPlaneClient`）。
2. 数据面把控制面的 **401** 统一映射成 503：
   `ConversationTurnService#toResponseStatus` 只对 400/403/404 保留状态，其余 `default -> SERVICE_UNAVAILABLE`。
3. 控制面 `InternalTokenFilter`（`/internal/*`）是 **fail-closed**：token 未配置时拒绝所有内部请求并返回 401。
4. 实测两个进程的启动环境：`AGENT_KNOWLEDGE_INTERNAL_TOKEN` / `KNOWLEDGE_INTERNAL_TOKEN` 均不存在
   （读取 PID 29628 / 44788 的进程环境变量，共 88 项，无任何 TOKEN 变量）；
   且 `aoteman-agent/config/application-local.yml`、`aoteman-controlplane/config/application-local.yml`
   都没有配置 `internal-token`。

结论：两侧内部 token 都是空值 → 控制面 `InternalTokenFilter` 拒绝 → 401 → 数据面映射为 503。

### 修复

1. 在两侧本地配置（`config/application-local.yml`，git 忽略、不入库）配置同一个随机 `internal-token`：
   - 控制面：`controlplane.knowledge.internal-token`
   - 数据面：`agent.knowledge.internal-token`
2. 重启 8080 / 8081 使配置生效。
3. 不改接口契约；不建议把 401 静默降级为「无专家」执行（设计 §10.3 要求选中专家后不静默降级）。

### 后续建议（本次不做，另开一轮）

`toResponseStatus` 把 401/500 一律折叠成 503，且不记录上游状态，导致「token 未配置」看起来像
「服务暂不可用」。建议：
- 401 → 502（网关/凭证错误）或 500，并在 message 中带上上游 HTTP 状态；
- 解析失败时打一条 WARN（含 expertIds 与上游状态），便于下次直接定位。
