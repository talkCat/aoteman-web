# 前端「等待工具」提示不明确，用户不知道在等什么工具

- 日期：2026-10-15
- 状态：已修复并验证（2026-10-18）
- 影响面：前端 `aoteman-web` + 数据面 `aoteman-platform/aoteman-agent`
- 证据工具：Chrome DevTools MCP（SSE 探针 + DOM 采样）

## 一、现象

前端偶现「等待工具」状态且等待较长，但界面上没有显示**具体在等哪个工具**，用户无法判断卡在哪里。

> 补充澄清：全仓库并不存在「等待工具」这句字面文案。用户实际看到的是工具行只显示 **「准备中…」+ 转圈**（`useSSEStream.ts` 里的占位名），以及过程块里的「过程 · N 步（含 N 次工具）」。所谓「不知道在等什么工具」，指的就是这段 **只显示占位名、不显示真实工具名** 的窗口。

## 二、复现与证据

用 Chrome DevTools MCP 注入探针（包装 `window.EventSource`、每 400ms 采样 `document.body.innerText`），发送「帮我做一份去成都旅游的ppt」，新会话 `1792302720508-vqpybk8f3`。

### SSE 时间线（相对发送）

| 时刻 | 事件 |
| --- | --- |
| +0.7s | `session.status_running`、`user.message` |
| +2.7s | `event_start`：payload 只有 `{ event_id, type: agent.tool_use }` —— **不含工具名** |
| +2.8s | `event_delta`：`delta: "{"`（工具入参 JSON 开始分片） |
| +4.8s~+4.9s | 更多 `event_delta`（入参 JSON 继续分片） |
| +5.2s | 落盘 `agent.tool_use`，**此时才带 `name: ask_followup_questions`** |
| +5.2s | `agent.tool_result`（RUNNING / `[Awaiting external execution]`） |

### DOM 时间线（关键证据）

| 时刻 | 画面 |
| --- | --- |
| +2.7s | 「过程 · 1 步（含 1 次工具）」+ **「准备中…」+「工具」+ 转圈** |
| +3.9s | 仍是「准备中…」 |
| **+5.6s** | 才变成 `追问问卷 工具`（真实工具名映射） |
| +6.0s | 问卷卡片渲染 |

➡️ 本次「准备中…」盲等窗口 **≈ 2.5s**。盲等窗口 = **工具入参 JSON 全部流完、落盘 `agent.tool_use` 的时刻** 减去 **`event_start` 的时刻**。`ask_followup_questions` 入参很小；对 `write_file` / `execute_shell_command` 这类**大入参**工具，整个 JSON 要流很久，盲等窗口会显著拉长 —— 与「等待时间长且不知道在等什么」完全吻合。

## 三、根因

三层叠加，缺一不可：

1. **后端预览帧不带工具名**
   `ConversationEventMapper.ToolCallStartEvent` 分支（约 188-204 行）此刻**已知 `toolCallName`**，但构造的起始帧 `new PreviewFrame(EVENT_START, toolUseTargetType(name), previewIds.toolUseEventId(id), null)` **没把名字带进 payload**。
   `ConversationEventPreviewBus.emitStart(...)`（25-30 行）也只发 `{ event_id, type }`。
   → 前端在 `event_start` 时拿不到工具名。

2. **前端占位名**
   `useSSEStream.ts` 的 `event_start` 命中 `agent.tool_use`/`agent.skill_use` 时，直接创建 `{ name: '准备中…', input: '', status: 'pending' }`（207-222 行）。
   随后的 `event_delta` 对该工具**只写 TRACE，不更新卡片**（239-244 行）。
   → 卡片只能等落盘的 `agent.tool_use`（带 `name`）到来才显示真名，而落盘发生在**入参 JSON 全部流完之后**。

3. **工具真名只在「入参流完」时才出现**
   落盘事件 `agent.tool_use`（`ToolCallEndEvent`）才有 `name`/`input`。于是「等待时长」正好等于「入参流式耗时」，且这段时长里界面只能显示占位名。

> 框架侧确认：`io.agentscope.core.ReActAgent` 在**工具名一确定**就发 `ToolCallStartEvent(replyId, toolId, toolName)`（2616-2618 行），此时名字已完整；`ToolCallDeltaEvent`（入参分片）随后才来。也就是说，**名字在 `event_start` 时刻其实已经具备**，只是我们的预览帧把它丢了。

## 四、影响范围

- 所有「模型发工具调用」的轮次都会经历这段盲等窗口；窗口长度 = 工具入参 JSON 的流式耗时。
- 入参越大越明显（`write_file` 写整段脚本、`execute_shell_command` 长命令等），用户感知为「卡住 / 不知道在等什么」。
- 追问问卷（`ask_followup_questions`）因入参小，窗口短，但也存在。

## 五、方案设计

原则：**让真实工具名在 `event_start` 的第一时间就到达前端**，把盲等窗口从「入参流完」提前到「工具调用开始」。

### 5.1 后端（aoteman-platform/aoteman-agent）

- `ConversationEventMapper.PreviewFrame`：新增可选字段 `toolName`（仅工具/技能起始帧使用）。
- `ConversationEventMapper`：
  - `ToolCallStartEvent` 分支：起始帧带上 `toolUse.getToolCallName()`。
  - `TextBlockDeltaEvent` / `ThinkingBlockDeltaEvent` / `ToolCallDeltaEvent` 分支：`toolName` 传 `null`（保持原语义）。
- `ConversationEventPreviewBus`：
  - `emitStart(...)` 增加带 `toolName` 的重载；当名字非空时，payload 追加 `toolName`。
  - `emitFrame(...)` 透传 `frame.toolName()`。
- `ConversationTurnService.dispatchMapped(...)`：起始帧改用带 `toolName` 的重载。

### 5.2 前端（aoteman-web）

- `useSSEStream.ts` 的 `event_start` 工具/技能分支：优先读 `payload.toolName`（兼容 `payload.name`），取到真名就用真名，取不到再退回 `'准备中…'` 占位。
- 不改动 `agent.tool_use` 落盘分支：卡片 id 与起始帧一致，`handleToolUse` 会按 id 合并，落盘后仍会用**权威名字 + 入参**覆盖，最终态不变。

### 5.3 副作用 / 替代方案

- 副作用：预览帧 payload 多一个字段，纯增量、向后兼容；老前端忽略该字段仍显示占位名，不报错。**未新增任何持久化事件**，历史回放不受影响。
- 替代方案 A（仅前端）：不建占位卡片、等落盘再显示 → 会让等待期界面**更空**，与「想让用户知道在等什么」相悖，否决。
- 替代方案 B（仅前端，靠 `event_delta` 拼名字）：`event_delta` 帧同样不含工具名，行不通；且要前端解析半截 JSON，复杂度高，否决。

## 六、验证方式

1. 后端编译 + 受影响单测通过（`ConversationEventMapperTest`）。
2. 重启 8080 数据面，用 Chrome DevTools MCP 探针复测：
   - 断言 `event_start`（`type=agent.tool_use`）的 payload 含 `toolName`。
   - 断言 DOM 从「准备中…」变为真实工具名的**时刻提前**到 `event_start` 附近（盲等窗口从 ~2.5s 缩到 ~0.1s 量级）。
3. 大入参工具（如 `write_file`）额外确认：盲等窗口只取决于「名字出现」而非「入参流完」。
4. 断言落盘后卡片最终仍显示权威名字与入参（无回归）。

## 七、修复与验证记录（2026-10-18）

### 7.1 已落地改动

- 后端 `aoteman-agent`：`ConversationEventMapper`（`PreviewFrame` 增 `toolName` 字段 + 起始帧携带 `toolCallName`）、`ConversationEventPreviewBus`（`emitStart` 增带名重载、`emitFrame` 透传）、`ConversationTurnService.dispatchMapped`（起始帧改用带名重载）；`ConversationEventMapperTest` 增 2 个用例。
- 前端 `aoteman-web`：`useSSEStream.ts` 的 `event_start` 工具/技能分支优先读 `payload.toolName`（兼容 `payload.name`），取到真名即用真名，否则退回 `准备中…`。

### 7.2 验证结果

1. 后端 `ConversationEventMapperTest`：`Tests run: 28, Failures: 0, Errors: 0`。
2. 前端 `tsc --noEmit`：通过（TypeScript 5.9.3，退出码 0）。
3. 重启 8080 数据面后用 Chrome DevTools MCP 探针复测新会话 `1792303384411-9ebfbbgrx`（「无锡今天天气怎么样？」）：
   - `event_start`（`type=agent.tool_use`）payload 已带 `toolName`，实测出现 `load_skill_through_path`、`execute`（两次）。
   - DOM 首次出现真实工具名 `load_skill_through_path` 于 `event_start` 后约 **73ms**；对照旧逻辑需等落盘 `agent.tool_use`（约 0.9s 后）才显示。
   - 全程 DOM 未出现「准备中…」占位（`准备中` 采样命中为 `null`）。
   - 落盘后卡片按 id 合并，最终显示权威名 + 入参（`load_skill_through_path · SKILL.md`），无回归。
   - 整轮 3 次工具调用正常收尾，最终答复正常渲染。
