# 权限规则重复保存返回 500

- 日期：2026-10-24
- 页面：`/admin/permissions`
- 状态：前端已规避（后端建议修复）

## 现象

1. 把 `write_file` 保存为「每次询问」→ 成功（POST 201，ruleId=1）。
2. 再保存为「拒绝」→ 成功，但列表出现两条 `write_file` 规则（ask + deny），计数为 2。
3. 再次保存「拒绝」（同一工具 + 同一行为）→ 页面提示「保存权限规则失败（500）」。

期望：同一工具重复保存即覆盖，只保留一条规则（设计 §4.2 ③）。

## 取证

浏览器 Network（Chrome DevTools MCP）：

- `POST /api/permission-rules` body `{"toolName":"write_file","behavior":"deny"}` → 201 `{"ruleId":2}`（首次 deny）
- 同一 body 再次提交 → 500 `{"error":"保存权限规则失败（500）"}`
- 两次请求之间没有 DELETE；500 来自 POST 本身，不是刷新 / 清理请求。

数据面日志 `D:\codex_pro\aoteman-platform\logs\aoteman-agent-error.log`：

```text
2026-10-24 14:27:42.785 ERROR ... 500 Server Error for HTTP POST "/api/permission-rules"
org.springframework.dao.InvalidDataAccessApiUsageException:
  The getKey method should only be used when a single key is returned.
  The current key entry contains multiple keys: [{GENERATED_KEY=2}, {GENERATED_KEY=3}]
    at GeneratedKeyHolder.getKeyAs(GeneratedKeyHolder.java:75)
    at GeneratedKeyHolder.getKey(GeneratedKeyHolder.java:65)
    at JdbcPermissionRuleStore.upsert(JdbcPermissionRuleStore.java:82)
```

同时观察到：这次失败的 POST 仍然改写成功了 `ruleId=2` 的 `updated_at`
（`updatedAt` 从 1792822901116 变为 1792823057247），说明数据库写入已提交，
异常发生在写库之后读取自增键的步骤。

## 根因

数据面 `JdbcPermissionRuleStore.upsert` 使用：

```sql
INSERT INTO ... ON DUPLICATE KEY UPDATE source = VALUES(source), enabled = 1, updated_at = VALUES(updated_at)
```

并通过 `Statement.RETURN_GENERATED_KEYS` + `GeneratedKeyHolder` 取回 `rule_id`。
MySQL 在 `ON DUPLICATE KEY UPDATE` 命中已有行时会先消耗一个自增值、再走 UPDATE，
`getGeneratedKeys()` 因此返回 **两行**（本次消耗的 id + 已有行 id）。
`GeneratedKeyHolder.getKey()` 在多行键时直接抛异常 → 全局异常处理返回 500。

## 影响范围

- 同一工具 + 同一行为重复保存：必然 500（虽然数据已更新，用户看到失败）。
- 同一工具切换行为：不会覆盖，而是新增一条；两行同时存在时权限引擎按 DENY 优先，
  用户以为改成了 ask，实际仍被 deny 拦住。
- 只影响 `/admin/permissions` 的保存动作；列表读取、删除正常。

## 处理方案（前端，本次实施）

后端未按“同一工具一行”实现（唯一键包含 `behavior`），前端不发送会触发该缺陷的重复 POST：

1. 若当前工具已存在相同行为的规则：复用该 `ruleId`，不再 POST（内容恒定为空串，
   无可更新字段）。
2. 若当前工具不存在相同行为：POST 新规则，成功后删除同工具的其余规则，
   保证界面上“同一工具只有一条规则”。
3. 删除旧规则失败时保留新规则并提示手动清理；POST 失败时不删除任何旧规则。

边界：POST 成功但清理失败 → 两条规则并存（提示用户手动删除），不静默吞掉。

## 验证

- `tsc --noEmit` / `next lint` 通过。
- 浏览器：`write_file` ask → deny（1 条）→ deny 再保存（成功，不新增）→
  再切回 ask（1 条）→ 删除（0 条，空状态）。
- 500 不再出现在 Network / Console。

## 建议（后端，另开一轮）

`JdbcPermissionRuleStore.upsert` 改用 `keyHolder.getKeyList()` 取第一条，
或改用 `queryForObject` 按唯一键反查 `rule_id`；更彻底的做法是把唯一键收敛为
`(user_id, tool_name)`，让 `ON DUPLICATE KEY UPDATE` 同时更新 `behavior`，
与设计“重复保存即覆盖”对齐。
