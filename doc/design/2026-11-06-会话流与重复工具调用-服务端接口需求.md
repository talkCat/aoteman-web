## 0. 结论摘要

前端实测到两个必须由服务端解决（或必须由服务端确认）的问题。当前前端已做降级，
但这两条**降级不了**：

| 编号 | 需求 | 优先级 | 前端能否单独解决 |
| --- | --- | --- | --- |
| **A** | 同一轮次内的重复工具调用必须被拦截 | **P0** | ❌ 不能（模型侧循环） |
| **B** | 会话流 attach 时补发"思考/正文"预览快照 | **P1** | ⚠️ 部分（前端可保持连接常驻，但断线即丢） |
| **C** | 主 Agent 显式迭代上限 / 单轮工具调用上限 / 超时 | **P0** | ❌ 不能 |

> 一句话：**A + C 负责"别再循环"，B 负责"切回来还能接着看"。**

---

## 1. 问题现象（前端实测）

### 现象 1：工具卡重复、追问反复弹出，形成自激循环

- 选择专家 + 深度思考提问后，过程时间线里同一个工具出现多张卡片；
- 卡片在「已完成」与「待执行」之间反复横跳；
- 追问（`ask_followup_questions`）提交一次后，过一会又弹出来，再次提交仍能发出；
- 服务端偶发 `503 Invalid tool result IDs`；
- 只能刷新页面终止。

### 现象 2：切换会话后看到的是"别人的"思考流

- A 会话正在深度思考时切到 B，B 会先看到 A 的思考文本；
- 切回 A 时思考文本**从头重放一遍**；
- Network 面板中同一会话出现多条 `after=0` 的 SSE 连接。

## 2. 服务端现状核对（逐条附证据）

> 以下均为**实际读代码**得到的结论，不是推测。

### 2.1 同一个 `toolCallId` 会落两条 `agent.tool_use`

`ConversationTurnService.handleAgentEvent()`（`ConversationTurnService.java:735-753`）在
`GenerateReason.TOOL_SUSPENDED` 分支里：

```java
dispatchMapped(sessionId, eventMapper.map(event, previewIds), startedTypes); // ① 已含 tool_use
persistSuspendedToolUses(sessionId, result.getResult());                     // ② 再补一条
turnContext.suspended.set(true);
```

`persistSuspendedToolUses()`（`ConversationTurnService.java:875-889`）用**同一个 `toolCallId`**
再 append 一条 `agent.tool_use`，且 `state` 固定为 `pending`：

```java
payload.put("id", toolUse.getId());
payload.put("toolCallId", toolUse.getId());
payload.put("state", "pending");
eventLog.append(sessionId, ConversationEventTypes.AGENT_TOOL_USE, payload);
```

**影响**：前端按 `toolCallId` 合并成同一张卡片时，第二条会把第一条的终态
（`success` / `error`）覆盖回 `pending`，于是"已提交的追问"看起来又能提交了。

### 2.2 主 Agent 没有显式 `maxIters`

- `AgentBeanConfiguration.java:117-118` 构建 `HarnessAgent` 时**未调用** `.maxIters(...)`；
- 作为对照，专家子 Agent 是有显式上限的：`ExpertAgentFactory.java:131`
  `.maxIters(expertProperties.getPerExpertSteps())`。

**影响**：主 Agent 走框架默认迭代数，模型反复调用同一工具时没有业务级刹车。

### 2.3 预览帧是热流、无回放

`ConversationEventPreviewBus.java:81`：

```java
sessionId, ignored -> Sinks.many().multicast().onBackpressureBuffer(512, false));
```

且预览帧的 `seq` 固定为 `-1`（`ConversationEventPreviewBus.emit()`）。

**影响**：后 attach 的订阅者收不到此前的增量。落库事件有补历史
（`ConversationEventLog.subscribe()` 注释明确"先补齐历史，再继续接收新事件"），
**预览帧没有**。所以"切走再切回来"这段思考文本天然丢失。

### 2.4 服务端本身允许同一用户多连接

`ConversationController.java:133` 的 `/{id}/events/stream` 每请求独立构建
`Flux.merge(persisted, previews)`（`ConversationController.java:171`），没有"每用户单连接"限制。

**结论**：多会话并行收流，服务端这一层**不需要改**；只需要确认网关/容器侧的连接数与时序限制。

## 3. 需求 A：同轮次重复工具调用拦截（P0）

分四小项，建议一起做。

### A1 事件层：同一 `toolCallId` 只表达一个状态机

**规则**

1. 同一 `(sessionId, toolCallId)` 只允许存在**一条** `agent.tool_use`；
2. 挂起不要靠"再补一条 pending"来表达，改为二选一：
   - **推荐**：新增事件类型 `agent.tool_suspended`，payload 同 `tool_use` 但 `state=suspended`；
     前端可直接把它渲染成过程时间线里的"等待确认"步骤，且不会破坏卡片状态机；
   - 保底：在原 `agent.tool_use` 上补字段 `suspended: true`，**不要重复 append**。
3. 任何 `tool_use` 重发/补发，`seq` 必须**小于**对应 `tool_result` 的 `seq`（前端按 seq 合并）。

**验收**：一次 `ask_followup_questions` = 1 条 `agent.tool_use` +（0 或 1 条 `agent.tool_suspended`）
+ 1 条 `agent.tool_result`。

### A2 执行层：轮次内工具指纹守卫

**位置**：Harness 中间件。

> ⚠️ 仓库红线（`Agent.md` §1）：属"使用框架能力"的第 ② 类。
> 落地前**必须先读** `https://java.agentscope.io/v2/zh/docs/building-blocks/middleware`
> 与 `/v2/zh/docs/building-blocks/tool`，确认拦截钩子名称、调用顺序、返回值约定，
> 把依据（类名 + 行号）写进实现注释。**禁止凭记忆写 API。**

**指纹**

```
fingerprint = sha256( turnId + "|" + toolName + "|" + canonicalJson(input) )
```

`canonicalJson`：对象 key 升序、去多余空白、数字规范化（`1` 与 `1.0` 视为同值）。

**策略**

| 第 N 次相同指纹 | 行为 |
| --- | --- |
| 1 | 正常执行，结果入本轮缓存 |
| 2 | **不执行**，直接返回第 1 次结果，正文前缀 `[duplicate-call-suppressed]` |
| ≥ 3 | **不执行**，返回结构化错误 `DUPLICATE_TOOL_CALL`，正文提示：<br>「该工具本轮已执行过，请基于已有结果直接作答，不要再调用同一工具。」 |

**范围与例外**

- 只在**本轮次内**生效；turn 结束（含挂起、中断、失败）立即释放缓存，跨轮次不共享
  （用户下一轮可能真的要重新检索）；
- 幂等写状态类工具可配置豁免（如 `todo_write`）；
- 不同参数的同名工具调用**不算**重复（例如分页、换 query）。

**配置项（`application.yml`）**

```yaml
agent:
  tool-guard:
    enabled: ${AGENT_TOOL_GUARD_ENABLED:true}
    max-identical-calls: ${AGENT_TOOL_GUARD_MAX_IDENTICAL:2}
    max-tool-calls-per-turn: ${AGENT_TOOL_GUARD_MAX_CALLS_PER_TURN:24}
    bypass-tools: []
```

### A3 硬性上限与超时

| 项 | 建议默认 | 超限行为 |
| --- | --- | --- |
| `agent.max-iters` | 12 | 正常结束本轮流式，输出已得内容 |
| `max-tool-calls-per-turn` | 24 | `session.error` + `code=TOOL_CALL_LIMIT_EXCEEDED` |
| 单轮墙钟超时 | 10 min | `session.error` + `code=TURN_TIMEOUT`，随后 `session.interrupted` |

错误文案要**人能看懂**，不要直接把异常栈丢给前端：

```
本轮工具调用已达上限（24 次），已停止执行。
请缩小提问范围，或拆成多个问题后重试。
```

### A4 `user.tool_result` / `user.tool_confirmation` 幂等

同一 `tool_use_id` 的第二次提交：

- **不要**再推进本轮、不要再 append 事件；
- 返回 **HTTP 200** + 幂等标记，而不是 5xx：

```json
{ "accepted": false, "reason": "DUPLICATE_TOOL_RESULT", "turnStatus": "running" }
```

理由：前端需要区分"用户手滑重复提交"（可忽略）与"服务端真故障"（需要重试提示）。
当前的 `503 Invalid tool result IDs` 让前端无法判断，只能整页刷新。

**验收**：连点两次"提交答案"→ 事件日志不新增 turn，页面不报错，问卷不复活。

## 4. 需求 B：会话流 attach 时补发预览快照（P1）

### 4.1 问题

思考 / 正文 token 走的是**预览帧**（`seq=-1`，热流）。切换会话、断线重连都会丢中间增量。
落库事件能补，预览帧不能。

### 4.2 方案（择一，推荐 B1 + B2）

**B1（前端先做，服务端只需确认）**

前端为每个打开过的会话保持一条常驻 SSE（最多 5 条，LRU 关闭空闲会话）。
服务端**无需改动**，只需回答：

- 单用户同时 3~5 条 `/events/stream` 是否有任何限制（Tomcat / 连接池 / 网关超时）？
- 空闲连接（长时间无事件）是否有服务端主动断开策略？如有，间隔多久？

**B2（推荐补齐，成本低、语义清晰）**

流建立时补发**一次**快照帧（仅预览通道，**不落库**）：

```
event: preview.snapshot
data: {
  "seq": -1,
  "sessionId": "1792823877410-gdph68lvf",
  "createdAt": 1762412345678,
  "payload": {
    "events": [
      {
        "eventId": "evt_xxx",
        "type": "agent.thinking",
        "text": "……已产生的完整思考文本……",
        "startedAt": 1762412340000
      },
      {
        "eventId": "evt_yyy",
        "type": "agent.message",
        "text": "……已产生的正文……",
        "startedAt": 1762412341000
      },
      {
        "eventId": "evt_zzz",
        "type": "agent.tool_use",
        "toolName": "knowledge_search",
        "inputJson": "{\"query\":\"...\"}",
        "partial": true,
        "startedAt": 1762412342000
      }
    ]
  }
}
```

**约定**

| 项 | 约定 |
| --- | --- |
| 时机 | SSE 订阅建立后立即下发；历史补发前后均可，前端按 `eventId` 覆盖 |
| 触发条件 | 仅当该会话存在 running turn 且存在未落盘的流式事件；否则不发 |
| 内容 | 每个 in-flight 事件一条，`text` 为**已产生的完整文本**（不是增量） |
| 兼容 | 老客户端不认识事件名会忽略（EventSource 按事件名订阅），无破坏性 |
| 之后的增量 | 仍用既有 `event_start` / `event_delta`，`event_id` 与快照一致 |

**B3（备选，不推荐首选）**

把 `multicast()` 换成 `replay(256)`，并给预览帧分配独立的单调序号
（字段名建议 `previewSeq`，**不要复用 `seq`**，避免污染落库游标）。
成本更低，但"回放多少、从哪开始"的语义更绕，且内存占用随会话增长。

### 4.3 前端配套（无需服务端）

- 每个会话独立 `lastSeq` 游标，**切换会话不再重置为 0**；
- 每个会话独立 `turnId`，不再共用一个全局计数器；
- 每条连接带 generation，旧连接晚到的事件一律丢弃；
- 会话在后台运行时不关闭连接，只在 LRU 超限 / 30s 无活动且非 running 时关闭。

## 6. 兼容与降级

- 前端当前**已有**的防御（服务端改完后仍保留）：
  - 按 `toolCallId` 合并卡片；
  - 按事件 id + `start:xxx` / `use:xxx` / `result:xxx` 命名空间去重；
  - 追问只认**最新一条** `pending` 的 `ask_followup_questions`；
  - 工具卡状态**不允许**由终态回退到 `pending`。
- 服务端新增字段全部**可选**：缺失时前端不渲染对应区块，不报错、不阻塞。
- 新增事件名（`preview.snapshot` / `agent.tool_suspended`）对老客户端是**无感**的。

## 7. 验收用例

| # | 场景 | 步骤 | 期望 |
| --- | --- | --- | --- |
| 1 | 单次挂起工具 | 触发一次 `ask_followup_questions` | 事件日志中 `tool_use` 恰好 1 条（或 `tool_use` + `tool_suspended` 各 1 条） |
| 2 | 重复调用 | 构造模型连续 3 次同参调用 `knowledge_search` | 第 1 次执行、第 2 次返回缓存、第 3 次 `DUPLICATE_TOOL_CALL`；本轮在 `maxIters` 内正常产出答案 |
| 3 | 重复提交 | 同一 `tool_use_id` 连续提交两次 `user.tool_result` | 第二次返回 200 + `DUPLICATE_TOOL_RESULT`，事件日志不新增 turn，页面不报错 |
| 4 | 调用上限 | 把 `max-tool-calls-per-turn` 调到 3，构造 4 次**不同**工具调用 | 收到 `TOOL_CALL_LIMIT_EXCEEDED`，前端显示可读错误，不无限 loading |
| 5 | 超时 | 把单轮超时调到 30s，构造长任务 | 收到 `TURN_TIMEOUT` + `session.interrupted`，前端回到可输入状态 |
| 6 | 快照续看 | A 会话运行中切到 B，30s 后切回 A | A 的思考文本**连续**，无断档、无从头重播 |
| 7 | 并发连接 | 同一用户同时打开 3 个会话 | 3 条独立 SSE，各自只收本会话事件，互不串台 |
| 8 | 回归 | 全量构建 | `mvn -o verify` 全绿；`AgentCapabilityPolicyTest` 覆盖新中间件 |

| A2 | ✅ 已实现 | 第 2 次同参调用复用首次结果（正文前缀 `[duplicate-call-suppressed]`），第 3 次起返回 `DUPLICATE_TOOL_CALL` |
| A3 | ✅ 已实现 | `max-iters` 默认 12；单轮工具总量默认 24；单轮墙钟超时默认 10 分钟 |

### 11.2 与上文描述的差异（前端必须按本节处理）

**1）`turnStatus` 不是固定的 `"running"`**

上文 A4 的示例写的是 `"running"`，实际返回会话的**当前状态**，取值可能是
`running` / `requires_action` / `idle` / `error`。它只用于提示与日志，**不要**拿它做分支判断。

**2）除 `DUPLICATE_TOOL_RESULT` 外，还有 `DUPLICATE_TOOL_CONFIRMATION`**

工具**确认**（`user.tool_confirmation`）重复提交时返回：

```json
{ "accepted": false, "reason": "DUPLICATE_TOOL_CONFIRMATION", "turnStatus": "idle" }
```

两个 `reason` 都按「静默忽略」处理：不弹错误、不回滚 UI、不重试。

**3）`DUPLICATE_TOOL_CALL` 是给模型的工具结果，不是给前端的错误码**

它出现在 `agent.tool_result` 的 `output` / `text` / `content` 里（形如
`DUPLICATE_TOOL_CALL: 该工具本轮已执行过相同参数的调用，请基于已有结果直接作答，不要再调用同一工具。`），
**不会**产生 `session.error`。验收用例 #2 的「收到 DUPLICATE_TOOL_CALL」
指的是工具卡结果里能看到这段文本，前端不需要为它做错误分支。

**4）`preview.snapshot` 只在请求携带 `event_deltas` 时下发**

`GET /api/conversations/{id}/events/stream` 的两个分支是互斥的：

- **不传** `event_deltas` → 只推落库事件，**没有任何 preview 帧**（含快照）；
- **传了** `event_deltas` → 先推一帧 `preview.snapshot`，再推 `event_start` / `event_delta`。

另外，attach 时若该会话没有未落盘的流式事件，**不会发空快照帧**，前端不要等它。

**5）预览通道有两套字段命名，不要混用**

| 位置 | 字段 |
| --- | --- |
| SSE 外层 DTO（所有帧） | `id`、`sessionId`、`seq`、`type`、`payload`、`processedAt`、`createdAt` |
| `preview.snapshot` 的 `payload.events[]` | `eventId`、`type`、`text`、`startedAt`、`previewSeq`（工具事件另有 `toolName`、`inputJson`、`partial`） |
| `event_start` 的 `payload` | `event_id`（下划线，历史协议）、`type`、`previewSeq`、`toolName`（可选） |
| `event_delta` 的 `payload` | `event_id`、`type`、`delta`、`previewSeq` |

注意外层是 `id` 而不是 `eventId`；快照里是 `eventId`。

### 11.3 `preview.snapshot` 帧结构（实测）

```json
{
  "sessionId": "1792823877410-gdph68lvf",
  "seq": -1,
  "type": "preview.snapshot",
  "createdAt": 1762412345678,
  "payload": {
    "events": [
      {
        "eventId": "evt_xxx",
        "type": "agent.thinking",
        "text": "……已产生的完整思考文本……",
        "startedAt": 1762412340000,
        "previewSeq": 17
      },
      {
        "eventId": "evt_zzz",
        "type": "agent.tool_use",
        "text": "{\"query\":\"...\"}",
        "toolName": "knowledge_search",
        "inputJson": "{\"query\":\"...\"}",
        "partial": true,
        "startedAt": 1762412342000,
        "previewSeq": 18
      }
    ]
  }
}
```

- `previewSeq` 是每会话独立递增的预览序号（用于前端丢弃乱序帧）；
- 事件一旦落库就从快照中移除，所以快照只包含「尚未落盘」的部分，历史部分仍由 `after=<lastSeq>` 补齐；
- 快照帧 `seq` 恒为 `-1`，**不要**用它推进 `lastSeq`。

### 11.4 配置项（服务端可调，前端只需知道默认值）

```yaml
agent:
  max-iters: ${AGENT_MAX_ITERS:12}
  turn-timeout: ${AGENT_TURN_TIMEOUT:10m}
  tool-guard:
    enabled: ${AGENT_TOOL_GUARD_ENABLED:true}
    max-identical-calls: ${AGENT_TOOL_GUARD_MAX_IDENTICAL:2}
    max-tool-calls-per-turn: ${AGENT_TOOL_GUARD_MAX_CALLS_PER_TURN:24}
    bypass-tools: ${AGENT_TOOL_GUARD_BYPASS_TOOLS:}
```

超时文案由服务端拼好，前端直接展示 `session.error.payload.message` 即可，例如：

```
本轮执行超过 10 分钟，已停止。可缩小问题范围后重试。
```

### 11.5 验收补充

- 用例 #2：观察 `agent.tool_result` 的输出文本，而不是等待 `session.error`；
- 用例 #3：重复提交后检查 HTTP 状态码为 **200**、响应体是**单个对象**（正常提交返回的是**事件数组**），前端按 `typeof body === 'object' && !Array.isArray(body)` 区分；
- 用例 #6：必须带 `event_deltas` 才有快照，否则该用例必然失败。
