# 2026-11-06 本轮产物尾部快捷预览（前端）

> 需求：PPTX 与 Markdown 一致 —— 每轮对话尾部列出**本轮产物**，点击卡片在原地展开**快捷预览**；
> 所有文本类产物都走同一套交互。
> 范围：仅前端（`aoteman-web`）。服务端接口契约见文末「服务端依赖」。

## 1. 背景与问题

现状（`src/components/TurnArtifacts.tsx`）：

- 卡片点击后**只能**跳到右侧 `ArtifactCanvas`，对话区被挤窄，看一行内容要来回切；
- PPTX 文案仍停留在「只提供下载」，与实际已上线的 PDF 预览通道不符；
- 只有 Markdown / PPTX 两种类型被识别，其它文本类型落到 `other`，直接「请下载后查看」。

目标：把「看一眼产物」的最短路径压缩到**原地一次点击**，画布退化为「深入阅读」的可选入口。

## 2. 交互规范

### 2.1 结构

```text
本轮产物  3  点击卡片即可快速预览
┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ [icon] 文件名 │ │ [icon] 文件名 │ │ [icon] 文件名 │   ← 卡片行（可换行）
│  MD  12.3 KB ⌄│ │ PPTX 41 KB  ⌄│ │ TEXT  2 KB  ⌄│     右侧独立「画布」按钮
└──────────────┘ └──────────────┘ └──────────────┘
┌───────────────────────────────────────────────┐
│ [icon] 文件名   复制  下载  在画布打开  收起 ×  │   ← 快捷预览（全宽，只在展开时挂载）
│ ───────────────────────────────────────────── │
│   正文 / PDF iframe（限高，内部滚动）           │
└───────────────────────────────────────────────┘
```

### 2.2 规则

| 规则 | 说明 |
| --- | --- |
| 单击卡片 | 展开 / 收起该产物的快捷预览（`aria-expanded`，`⌄` 旋转 180°） |
| 同时只开一个 | 展开 B 时自动收起 A，避免一屏多个 iframe |
| 画布入口 | 卡片右侧独立按钮（`PanelRight` 图标），不嵌套在卡片按钮内 |
| 展开定位 | 展开后 `scrollIntoView({ block: 'nearest' })`，避免预览长在视口外 |
| 高度上限 | Markdown / 文本 `max-h-[min(58vh,520px)]` 内部滚动；PPTX `h-[min(56vh,480px)]` `min-h-[320px]` |
| 下载 | 每个类型都保留，且与预览状态解耦（预览失败仍可下载） |
| 演示产物 | `?preview=1` 下不请求服务端、不伪造 PDF，按钮置灰并给 title 说明 |

## 3. 类型矩阵

| kind | 判定 | 快捷预览 | 画布 |
| --- | --- | --- | --- |
| `markdown` | `.md` `.markdown` `.mdx` | `Markdown` 组件渲染 | `MarkdownArtifactView` |
| `text` | 文本扩展名（txt/json/yaml/csv/html/js/py/java/sql/log/toml/ini/sh/ps1…）或 `text/*` MIME | 等宽 `<pre>` + 复制 + 下载 + 行数 | 新增 `TextArtifactView`（同源组件，`variant=canvas`） |
| `pptx` | `.pptx` | 复用 `PptxPreviewPane` + `useArtifactPreview`（PDF 通道、骨架、失败重试） | `PptxArtifactView` |
| `other` | 其余 | 不支持内嵌，给下载按钮 | 下载提示 |

判定集中在 `src/lib/artifacts.ts#artifactKind(path, mimeType)`，**不按文件内容猜**：二进制文件永远不请求正文。

## 5. 服务端依赖（未就绪的部分）

现状：`aoteman-agent` 的 `SyncArtifactContentStore#isSupported` 只认 `.md` / `.markdown` / `.pptx`，
`/api/artifacts` 列表也只返回这三类；`/api/artifacts/content` 对其它类型返回 415。

因此前端本轮做的是**平滑前置**：

1. 后端返回文本类产物时，列表 → 卡片 → 快捷预览 → 画布全链路**无需再改前端**；
2. 后端未放开前，这些文件不会出现在 `/api/artifacts`，界面上自然不可见，不会出现空卡片；
3. 万一拿到无法读取正文的产物（415/404），快捷预览展示错误 + 重试 + 下载，不阻塞对话。

后端放开时建议同步：

- `isSupported`：`text/*` 与常见文本扩展名（与前端 `TEXT_EXTENSIONS` 保持一致）；
- 列表接口 `mimeType` 返回真实 MIME（前端仅在扩展名缺失时用它兜底）；
- 二进制类型继续 415，避免前端误把字节流当文本渲染。

## 6. 产物归属识别：为什么不能只看 `input.path`

对照真实会话（政策专家 → 「帮我生成对应的ppt」，session `1793971812266-8oi8fbpfz`）发现：

```text
write_file  ppt_temp/generate.py     ← 源码里写着 out_file = ".../xxx.pptx"
execute     python generate.py       ← 命令文本里没有 .pptx
```

PPT 技能链路「写脚本 → 执行脚本」两条工具调用的 `input.path` / `command` 都**不含** `.pptx`，
按写入路径精确匹配会漏掉整张卡片。因此 `artifactPathsFromToolUse` 的规则是：

| 工具 | 取值 |
| --- | --- |
| `write_file` / `edit_file`（产物扩展名，且不是脚本） | 直接取 `input.path` |
| `write_file`（脚本扩展名 `.py` / `.js` / `.sh` …） | 从 `input.content` 里扫 `.pptx` 路径；**脚本本身不入列** |
| `execute` / `bash` / `shell` / `run_command` | 从命令文本扫 `.pptx`，相对路径按 `workingDirectory` 补齐 |

多提取的候选路径会因匹配不到 `/api/artifacts` 的真实列表而自动消失（宁多不漏）；
脚本扩展名本身也在文本扩展名集合里，所以**必须先判脚本、再判产物**，否则 `generate.py` 会顶替真产物。
